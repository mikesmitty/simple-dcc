## Train Control standard fixes

Found comparing simple-dcc against the Train Control standard (S-9.7.4.1) and OpenMRN. JMRI never reads a train's protocol bits or asks for Is Train (it builds the node ID from the DCC address and sends Assign Controller straight to it), which is why the second and third went unnoticed. The e-stop bug hits JMRI too: its e-stop button sends the Emergency Stop instruction (`TractionThrottle` in OpenLCB_Java).

- **Emergency stop doesn't stay stopped (safety).** `dcc_emergency_stop` and `dcc_emergency_stop_all` in `src/dcc/dcc.c` send the e-stop packet but leave each loco's stored `speed_step` alone, and `dcc_update` re-sends that speed on its next pass (11 loop states x 5 ms, about every 55 ms), so the train starts again. Found by reading the code; confirm on the main with someone watching a moving loco. What §6.2 asks for:
  - A train's Emergency Stop instruction sets its Set Speed to zero, keeping direction.
  - Global Emergency Stop (event `01.00.00.00.00.00.FF.FD`) holds every train stopped *without* changing its Set Speed. On Clear Emergency Stop (`...FF.FC`) each train accelerates back to its Set Speed. Global Emergency Off behaves the same way, and track power already covers it.
  - So: zero the stored speed on a train e-stop. Add a held global e-stop state that the reminder loop honors, sending e-stop instead of the stored speed, and that Clear Emergency Stop releases. Set the e-stop bit in the Query Speeds status while it's held.
  - Then the Emergency Stop pair can report Valid/Invalid through `lcc_events_register`'s state callback, like the Emergency Off pair does (`power_event_state` in `src/protocol/lcc_interface.c`).

- **Train nodes advertise the wrong protocol bit.** `LCC_PIP_TRAIN_CONTROL` in `src/lcc/lcc_defs.h` is `1ULL << 30`, which is Function Configuration. Traction Control is `1ULL << 34` (`TRACTION_CONTROL = 0x000400000000` in `~/git/openmrn/src/openlcb/Defs.hxx`; Interlock's `openlcb/pip.go` agrees). It has been wrong since the M2 skeleton (`30f24da`). Interlock's node view lists simple-dcc trains as "Function Configuration", and any client that checks PIP before treating a node as a train will skip them. While there: train nodes serve CV space 0xF8 for programming on the main (`lcc_traction_register_cv_space`), but the PIP set in `train_allocator` (`src/protocol/lcc_interface.c`) leaves out Datagram and Memory Configuration.

- **Train nodes don't produce Is Train.** §6.4: train nodes shall produce the well-known event `01.01.00.00.00.00.03.03` (`IS_TRAIN_EVENT` in OpenMRN `TractionDefs.hxx`, `EventIsTrain` in Interlock's `openlcb/traction/traction.go`). Nothing in `src/` registers it, so Identify Producer on it finds no simple-dcc trains. Registering it per train node in `train_allocator` would overflow `LCC_MAX_EVENT_REGISTRATIONS` (16): the CS uses 5, and the pool holds `LCC_MAX_NODES - 1` = 23 trains. Either grow the table or have `lcc_events.c` answer it for every train-role node without a table entry.

## LCC protocol

- **DCC accessory decoders through the well-known accessory events.** There's no accessory packet support at all yet. Consume `01.01.02.00.00.FF.xx.xx` (activate) and `01.01.02.00.00.FE.xx.xx` (deactivate) for basic accessories, plus `01.01.02.00.01.xx.xx.xx` for extended accessories (signal aspects), and send the matching DCC accessory packets. This is the biggest functional gain on the list: JMRI turnouts, Interlock levers and automations, and any LCC node could throw turnouts on DCC accessory decoders, and Interlock's simple-dcc profile could list them as turnout entities.
  - Address math: `accy_normal_event` / `accy_reversed_event` in OpenMRN `TractionDefs.hxx` (event = `ACTIVATE_BASIC_DCC_ACCESSORY_EVENT_BASE + (binary_addr << 1)`, `+ 1` for normal). Reference consumer: `DccAccyConsumer.hxx`.
  - 4096 events don't fit the registration table: answer Identify with Consumer Range Identified (as `DccAccyConsumer::handle_identify_global` does) and match Event Reports by prefix.
  - Needs accessory packet builders in `src/dcc/packet.c`, and per-address last state if Identify Consumer should say Valid/Invalid the way OpenMRN does.

- **Remote consist slaves — alias resolution.** `forward_to_consist` in `src/lcc/lcc_traction.c` silently skips any consist member whose node ID doesn't resolve to a locally-registered `lcc_node_t`. Fine for a standalone CS where every consist member is a local train proxy, but it breaks multi-CS consists and consists that include an external LCC-enabled loco. It also means throttles attached as listeners get nothing forwarded: JMRI attaches itself as a listener after Assign Controller to follow other throttles' commands, and gets an OK but no forwarded commands from simple-dcc. Three reasons it was deferred in M8:
  1. **Addressed messages are alias-keyed, not node-ID-keyed.** `lcc_node_send_addressed` in `src/lcc/lcc_node.c` bakes `dst_alias` into the 2-byte addressed header — we have the alias for local nodes via `lcc_node_t.alias`, but nothing maps a remote node ID to its current alias.
  2. **No alias-resolution machinery.** OpenMRN's iface transparently resolves `NodeHandle{id, alias}` by issuing `VERIFY_NODE_ID_GLOBAL` with the target node ID and waiting for `VERIFIED_NODE_ID`. We'd need an alias cache, a pending-forward queue, and retry/timeout state — separate from consist itself (~150 LOC).
  3. **Aliases rotate.** `CNSTFLAGS_ALIASVALID` lets the throttle supply the slave's alias at ATTACH time (bytes 9-10 of the ATTACH payload — currently ignored). A cached alias can go stale on conflict-driven re-allocation, so any cache also needs invalidation on AMR / RID-collision traffic.

- **`REQ_TRACTION_MGMT` (`0x40`): Reserve/Release and heartbeat.** Sub-commands per OpenMRN `src/openlcb/TractionDefs.hxx:128-131`: `MGMTREQ_RESERVE` (`0x01`), `MGMTREQ_RELEASE` (`0x02`), `MGMTREQ_NOOP` (`0x03`). Today a `0x40` message hits `default: break` in `src/lcc/lcc_traction.c` and gets no reply.
  - **Reserve/Release** is a cooperative soft-lock beside Controller Assign (`0x20`), not a replacement; OpenMRN's train keeps a `reserved_` bit and refuses a second Reserve (`TractionTrain.cxx:558-580`). Deferred from the v1 LCC rewrite because JMRI's throttle path uses Controller Assign. Before implementing, read `TractionTrain.cxx` to confirm how Controller Assign and Reserve interact.
  - **Heartbeat** (Train Control §6.6) is the useful half: a train with a nonzero Set Speed may send its controller a Heartbeat Request (`MGMTRESP_HEARTBEAT` + deadline in seconds); any command or query, or a No-op, clears it, and if nothing arrives by the deadline the train takes it as Set Speed 0 and forwards that to its listeners. No heartbeat at zero speed or with no controller assigned. This stops a train whose throttle vanished mid-run (a phone off Wi-Fi, Interlock quitting). OpenMRN's throttle answers heartbeats on its own (`TractionThrottle.hxx:527`), and so does JMRI (`handleHeartbeatMessage` in OpenLCB_Java's `TractionThrottle.java`). Interlock doesn't yet: it only matches a Traction Control Reply to a request it sent, so it would drop the request and its trains would stop at the deadline. Fix that in Interlock before turning this on. Landing spot: handler beside the consist (`0x30`) handler; per-train deadline on `lcc_train_state_t`; a 1 Hz tick off `lcc_task.c`.

- **Function and train names (FDI).** Space 0xFA (Function Definition Information, read-only XML per train, PIP `TRACTION_FDI` = `0x000200000000`) tells throttles each function's label and whether it's momentary. Train names would go in the SNIP user name, writable through ACDI 0xFB on train nodes. Both need storage keyed by DCC address that outlives the train node. Interlock already keeps a roster with each loco's decoders, so decide which side owns names before building this.

- **Firmware Upgrade protocol.** Freeze/Unfreeze plus writes to space 0xEF (PIP `FIRMWARE_UPGRADE` / `FIRMWARE_UPGRADE_ACTIVE`) so JMRI's firmware updater, or Interlock if it grows one, can flash the board over LCC instead of BOOTSEL and copying the file. Most useful once the board sits on CAN through the MCP2515. The RP2350's A/B partition boot is a natural way to stage the new image.

- **Considered and skipped for now:** Broadcast Time (fast clock), the function values space 0xF9 (optional in §7.1; Set Function covers it), and the Stream protocol.
